# 历史规划归档（截至 0.12.0）

此文保留早期设计、原版本拆分和迭代过程，不代表当前待开发清单。当前状态与排期以[主规划](feature-plan.md)为准。

# chat-agent 智能陪伴功能迭代计划

更新：2026-11-03。已按用户要求一次完成 **0.9.1、0.10、0.11** 三个方向，统一发布为 **0.11.0**，见[联合交付说明](release-0.11.md)。模型自主工具运行时、记忆纠错和关怀节奏已接入现有平台；0.12 已实现点选朗读与 Android 系统识别草稿，见[语音说明](release-0.12.md)。

## 产品主线

围绕同一个陪伴角色，逐步做到：听懂当下需要 → 记得共同经历 → 自然接续话题 → 在用户愿意时主动关心 → 一起形成日常生活中的小习惯。

判断功能价值时，优先问“它是否让下一次交流更贴近这个人”。默认的“小伴”承接主要陪伴体验，已有“计划伙伴”保留为按需使用的辅助角色。搜索、提醒、会话管理和设备能力服务于这条主线。

**平台优先级：先在现有 Android 应用和网页中完善陪伴体验。** QQ、微信、B站等第三方 IM/社区接入为低优先级，不作为聊天节奏、记忆或主动关怀功能的前置条件；本阶段不开发平台适配器、不部署账号网关、不接入外部账号。开源项目中的自然交流设计可直接适配 chat-agent 自有界面。

## 规划前基线（0.3.0）

- 已有“小伴”的人格、交流规则和风格文档，但尚无系统化的陪伴偏好配置、跨会话事件接续与关怀调度。
- 已有角色隔离、审核记忆、上下文压缩和待办/提醒工具，可直接作为基础。
- 已有 ecnu-max、服务器搜索、Android 加密连接、自动登录与应用内更新；不重复建设客户端和运行时。
- 当前只有提醒收件箱，没有关闭应用后的系统通知。长期记忆默认仅在用户明确要求时提出候选，审核通过后生效。

## 技术栈评估与建议

当前建议保留 Go 主服务。0.4–0.6 的主要工作是通过 API 调用模型、装配上下文、存储关系状态和调度关怀，现有工程已具备对应基础。借鉴 Python 或 TypeScript 项目的机制不要求使用相同语言；更换语言本身不会改善模型表达或记忆准确性。

- Go：继续负责 Agent loop、陪伴偏好与事件、上下文构建、权限、调度、加密入口和模型请求。新增陪伴领域模块，避免把全部逻辑继续堆入现有 API 组装函数。
- 数据：JSON/JSONL 先沿用；检索、关联查询或事务一致性成为实际瓶颈时评估 SQLite 和所需驱动。更换存储可单独进行，不与语言重写捆绑；标准库优先不等于永远拒绝必要依赖。
- Python：若以后需要在自己的设备运行 ASR/TTS、embedding、重排或训练，先验证具体模型与运行库，确有需求时通过本机 HTTP/独立进程接入。当前不预先增加服务或在小内存服务器加载本地模型。
- Kotlin：继续负责 Android 原生能力；网页当前继续使用原生 JavaScript，界面规模增长后再独立评估 TypeScript。

Go 的网络能力参见[标准库 net/http](https://pkg.go.dev/net/http)；需要 Python 模型运行环境的代表例子参见[PyTorch 安装说明](https://pytorch.org/get-started/locally/)。这些生态能力提供选型依据，具体拆分仍以实际功能与部署约束决定。

只有在核心工作长期集中于 Python 专用模型库、Go 与辅助进程之间的数据搬运和部署成本持续高于收益，或小规模原型证明另一语言能明显简化核心功能时，再考虑主服务迁移。先记录实际维护、延迟和资源问题，再决定，不仅依据参考项目的语言重写。

## 第一批：0.4.0 陪伴对话核心

### 具体体验

1. **稳定的人格**：小伴的称呼、表达风格和交流边界在会话切换后保持一致。已有个性化角色文档保留；更新默认模板时不能覆盖用户修改。
2. **少量可调偏好**：用户可设置希望怎样被称呼、回答长短、表达温度、是否喜欢追问和建议；支持在聊天中说“先听我说”“简短一点”。明确修改长期偏好的指令可以保存，临时要求仅影响当前交流。
3. **灵活的交流方式**：支持“听我说”“陪我聊”“一起想办法”。默认随对话自然调整，用户一句话即可切换；不要求每轮选择模式。
4. **回应当轮感受**：先回应用户实际表达，再决定是否追问、分享话题或给建议。不把推测的情绪当成确定事实，也不把一次低落写成长期性格标签。
5. **有连续性的追问**：围绕用户刚才说的具体事情继续交流，避免每轮重复欢迎、反复问同一个问题或同时追问很多件事。
6. **保留真实依据**：没有记忆依据时可以询问，不编造共同经历、离线活动或已经完成的关怀。

### 实现切分

- 陪伴配置：在角色范围内保存结构化偏好，复用现有 JSON 存储；与角色 Markdown 协作，明确临时指令、用户保存的偏好和默认值的优先顺序。
- 上下文装配：当前消息与临时要求优先，其次为明确保存的陪伴偏好、相关已审核记忆和角色默认风格；历史与检索内容不能升级工具权限。
- 提示与 Skills：完善小伴的倾听、闲聊和协作表达策略，使用已有按需 Skills 机制；不通过无限增加提示词堆叠人格。
- 推理成本：首版在现有一次回答中完成交流方式和语气调整，不为每条消息额外调用一个情绪分析模型，也不单独持久化情绪评分。
- 网页入口：角色设置中增加轻量陪伴偏好，聊天里提供可选的快捷表达；主界面仍以对话为中心。

### 首版验收

固定使用三段短场景人工体验：

- “今天有点累，先别给建议。” → 先倾听，围绕已表达的内容回应。
- “现在帮我想一个能做到的小办法。” → 自然转向协作，不重复前面的倾听模板。
- “以后叫我小李，回复短一点。” → 保存明确的偏好修改，重启/新会话后仍生效；临时的“这次详细讲”不会改掉长期偏好。

只新增一条偏好持久化与作用域的集成检查，运行相关已有检查。语言体验用上述小场景判断，不写逐字匹配生成回复的测试，也不创建完整评测平台。

## 最近一批：0.4.1 现有平台的自然聊天节奏

- 现有输入框在回复时仍可编辑，新消息显示明确的待发送状态，并进入有界队列。
- 在尚未发起模型请求的小窗口内聚合连发消息，保留用户原来的消息边界；已经开始的请求期间，新消息按会话串行排队，不每收到一句就取消并重发收费请求。
- 陪伴交流按语义组织为少量短句气泡，代码、列表和需要完整解释的内容保持结构。分段复用一次生成结果，不为每个气泡单独请求模型。
- 每次提交和回复分段都有稳定标识，刷新和重连后不重复提交、不重复展示；已显示内容、生成完成状态和未完成内容要能区分。
- 明确停止时取消当前生成和未发送的回复气泡；排队用户消息保留并提供继续/撤回入口，停止后不自动启动下一次模型调用。退出或重连不隐式重放已执行工具。
- 低延迟优先，等待用于合并连发和处理发送顺序，不靠长时间模拟打字制造自然感。

最小验收为一条手机流程：连续发几句话 → 聚合后回复 → 回复期间继续输入 → 停止 → 刷新，确认顺序、去重、待发送状态和后续模型调用一致。只补充必要的队列/持久化边界检查，不增加第三方平台测试。

## 第二批：0.5.0 长期关系与记忆

### 记忆分层

- **稳定事实和偏好**：称呼、兴趣、交流习惯等，复用已有审核与纠错能力。
- **重要事件**：用户愿意保留的经历、未来事件及其后续，例如“周五有面试”；记录来源、事件时间、当前状态和是否允许之后提起。
- **未完话题**：用户愿意继续聊的事情，以及上次聊到哪里；不直接保存整段私密倾诉作为永久画像。
- **短期状态**：只用于当前交流，默认不升级为长期记忆；如要跨会话保留，适用同样的授权与管理入口。

### 记忆行为

用户明确说“记住”“下次再聊这个”时保留对应内容。自动整理候选可以作为用户主动开启的可选能力；默认沿用当前明确授权与审核机制，不静默改变现有策略。一次设置允许自动提取候选后无需每轮询问，但候选仍不等于已审核事实。

每条长期记录能查看来源、修改、删除或设为不主动提及。用户当前纠正优先；已删除或被替代的记录不再进入后续检索。已有聊天、摘要和备份中的副本要单独说明和处理，不能把删除一个记录宣传为所有副本已清除。

跨会话接续先选少量相关事件和话题，不每次开场都翻旧事。首次落地优先复用关键词检索、时间和事件状态，不预先引入向量数据库。侧面元数据独立版本化，避免直接扩展严格校验的旧 JSONL 记录。

最小验收：一条“授权保留事件 → 新会话接续 → 用户纠正/删除 → 后续不再使用旧内容”的集成流程，加一次真实语言体验。

## 第三批：0.6.0 有边界的主动关怀

### 关怀从具体事情出发

- 用户同意的事件后续：“面试结束后，可以问问我怎么样了。”
- 用户设置的固定问候时段或轻量复盘。
- 用户返回应用时，围绕允许继续的未完话题自然接续。

设置提供开关、频率上限、安静时段、暂停和不再提及某个话题。用户只说“周五有面试”不自动等同于授权后台问候；关怀意愿可以通过一句明确指令或统一设置表达。

### 先实现可验证的触达

第一步做服务器持久化的关怀计划与收件箱，在用户打开应用时展示允许生成的问候。模型只生成措辞，是否到期、是否允许、是否已发送由服务端状态判断；任务有唯一标识，重启或重复请求不能重复触发。

自动生成问候需要用户开启并配置调用预算；每个关怀事件限制生成次数，失败不反复调用付费模型。主题过期或用户取消后停止，未回复不会提高发送频率。

随后验证 Android 本地通知和同步条件。已同步的计划才有条件在本机触发；其他设备新增计划在尚未同步时不能保证通知。需要额外推送渠道时再单独决定，不提前承诺关闭应用后的可靠到达。

最小验收覆盖到期、安静时段、去重、停用与取消，一次真机检查通知条件；不做庞大的设备矩阵。

## 第四批：0.7.0 共同活动与表达形式

先提供几个能自然延续的场景：睡前聊一会儿、一天里的一件小事、围绕共同兴趣聊一个话题、用户选定的小目标陪伴。保存的进度要有用户意愿依据，并能暂停、结束或换话题。

搜索只在话题确实需要外部事实时使用，来源可追溯；提醒只在用户要设置时创建。活动进度服务交流，不用打卡分数或关系等级代替实际对话质量。

文字体验稳定后再评估语音消息。先核对服务端可用的识别/合成能力、延迟和成本，再决定录音上传、转文字与播放；暂不承诺实时通话，也不让手机直接持有模型 API Key。

## 支撑工作与优先级调整

此前规划中的会话搜索、命名、归档、导出、文件问答和资料收藏移入按需待办：只有在帮助接续话题、回看共同经历或用户明确需要时再实施，不占据下一版的核心范围。

第三方 IM 与社区接入统一留在低优先级待办。下一阶段所有主要体验验收均在 chat-agent Android/网页完成，后续是否接入外部平台由用户另行指定。

断线状态、消息去重、备份恢复、调用预算和设备凭据撤销仍是运行保障，按是否直接影响陪伴体验穿插修补。主动关怀上线前必须具备去重、停用和预算边界；跨会话记忆扩展前必须明确修改、删除与恢复行为。

继续独立实现运行时，优先标准库，不导入外部 Agent 项目。每轮保留少量关键状态测试和短对话体验，不做无必要的完整矩阵或独立审查委派。
