## 1. 概率闸门与可观测的沉默

### 当前基础

`web/life.js` 在应用可见、联网、用户启用自动关怀且没有聊天等冲突时发起检查。`LifeStore.ClaimCare` 已检查启用状态、安静时段、暂停、最小间隔、事件版本与每日尝试额度；尝试在生成前持久化，失败仍计入额度，不自动重试。因此当前成本已有硬上限，并非每次前端轮询都会收费。

`runCare` 随后检索参考，可能调用配置的远端 rerank，再用 `probe.Generate` 做一次无工具问候生成。概率抽样必须先于这些潜在付费步骤。

### 拟实现的链路

```text
满足自动闲聊问候条件
  -> 查角色/日期/时段的稳定机会 ID
  -> 已决定：返回原决定，不再次抽样
  -> 未决定：本地随机抽样，并原子持久化结果
       -> 未命中：记 silent/skipped，零模型和 rerank 调用
       -> 命中：检查/预留尝试额度 -> 检索参考 -> 生成 -> 原有结算
```

- 同一机会只抽样一次；刷新、多设备检查、重启和并发不能反复抽到命中为止。持久化失败不调用模型；需明确决定与预留额度的原子提交边界。
- 抽样概率是节奏参数，不代表 LLM 理解了是否适合说话，也不增加分类模型。首版默认 50%，可在现有设置中调整为 0–100%；不把插件示例值视为本产品承诺。
- 未命中不消耗模型尝试额度，但消耗本次机会；失败/中断继续计入已有尝试额度，不自动重抽或重放。
- 仅作用于用户已启用的可选自动闲聊问候。用户手动生成、明确时间的提醒和获准事件跟进不被随机取消；它们仍遵守各自预算和安静时段。
- 运行记录至少保存机会 ID、角色、计划时间、策略版本和结果。未命中进入有界运行记录，不制造一条未读问候、不发通知，也不声称“今天完全没开口”。
- 每日额度提供硬上限，概率仅降低平均调用量；不承诺命中后的模型调用免费、固定 token 消耗或确定节省比例。
- 首版保留应用可见时检查和现有收件箱。服务端后台调度、可靠手机触达仍未实现，不因增加骰子而宣称具备它们。

0.26 已实现本项目的受限 followup：可信主动来源、已有会话目标、稳定请求 ID、一次模型响应、零工具，并明确不把后台触发当作用户授权。它不是完整自动工具回合。

改动位置预计为 `internal/companion/life.go`、`internal/api/life.go` 和必要的设置/状态展示。新增持久字段或状态需显式处理旧读取器兼容，不能假定现有严格 JSON 读取器自动忽略。

## 2. AI 提议改人设，用户审核后生效

现有角色由 IDENTITY.md、PROFILE.md、RULES.md 和 Skills 组成；会话固定角色，现有界面选择其他角色创建新会话，并非任意改写旧会话归属。角色文件目前可由用户修改，缺少 AI 提议、候选审核和基于旧内容的冲突检查。

已增加 `role_change_propose` 工具，和现有工具一样集中定义 schema、Usage、宿主约束及执行函数。模型只能生成候选，不能调用现有角色文件更新接口绕过审核。

- 首版只开放 PROFILE.md 的表达风格候选；需要扩展 IDENTITY.md 时同样逐项审核。RULES.md、系统约束、权限和其他角色文件不属于此工具的修改范围。
- 候选记录包含角色、目标文件、原内容 hash、建议内容、简短理由与来源会话；“允许提议”不等于“允许写入”。持续自动提议需单独明确开启，默认不产生后台演化。
- 可复用记忆审核面板的交互方式，但人设候选需独立类型与应用路径。批准记忆事实不能顺便修改角色文件。
- 审核显示实际差异；批准时在角色管理器锁内比较原 hash，再原子替换。期间用户修改了原文件则返回冲突，不覆盖；拒绝不修改任何角色文件。
- 保留当前审核与保存边界：表达偏好仍可用既有偏好工具，不把每次临时聊天风格都升级成人设候选。
- 新人设用于后续请求；正在执行的一轮使用已有角色快照。候选支持查看和删除，正文副本纳入相应隐私清理范围。

不引入工作区概念，不把当前角色机制扩展成 DSH 的工作区/会话人设卡兼容层。

## 3. 克制的作息与共同话题漏斗

用户已授权，本次以显式配置的公开兴趣查询、直接网页读取实现。首版不自动提取共同活动或私人记忆作搜索词；范围包括：

- 在用户允许的时间窗口内预先抽取有限唤醒时刻并持久化；不因重启补发一串错过的内容，不在安静时段追赶额度。
- 允许整个机会或当天不采集；“不采集”和“已采集但不发送”分别记录，避免把无动作包装成已经体验过内容。
- 有界漏斗：少量候选、去重、选择少量正文深读，最终可选零条。候选 5 条、深读 2–3 条作为初始设计预算，不保证搜索或解析必有足够可用内容。
- 发送约束同时保留每日生成尝试预算、最小间隔和未读克制。拟为可选主动话题设置每天最多 3 条的用户级硬上限，跨角色共享，不能靠多角色扩大；不静默改写现有明确跟进计划。
- 若保留“两本日记”，分别作为可查看/删除的内部运行笔记和实际给用户的分享记录。内部笔记记录来源、筛选和已执行结果，不保存隐藏推理，也不自动固化用户画像。
- 不接 Cookie、扫码、账号自动操作、平台风控绕过或评论监听。将来需要账号平台接入时，作为独立需求评估。

搜索、正文获取、生成和发送预算分别计数。符合概率或数量限制不等于已经获准后台抓取、写长期记忆或发送通知。

## 最小检查与交付边界

三项机制和 0.26 同会话 followup 已完成实现、最小检查与部署，没有新增真实模型验收。后续检查继续保持少量关键流程：

1. 闸门：用可控随机源覆盖未命中零调用、命中一次；同机会并发/重启不重抽，手动及明确跟进不受概率影响。
2. 人设：一条提议→审核→应用流程，覆盖原文件未批准不变、基础 hash 冲突、角色与文件范围限制。
3. 内容源：实施时再覆盖一次有限漏斗，含零输出、全局上限和失败不补发；不提前构建完整矩阵。

如后续直接借鉴插件源码或提示词，实施前补齐可访问的上游地址、固定版本和许可证核验，并更新来源清单；本规划不等于已经完成三插件源码迁移。
