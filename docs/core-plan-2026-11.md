## 2. 产品顺序

先让现有 CA 连续、可靠地聊天和调用已有能力，再扩展服务器和本地执行端与持续成果。沿用现有 Go、原生 JS 与 Kotlin 架构，按能力引入许可适用的上游代码与组件。客户端工作集中在新能力交互和真实使用问题。

| 阶段 / 暂定版本 | 交付范围 | 完成标准 |
| --- | --- | --- |
| A · 0.29.x 收口 | 对齐发布事实；收口工作区 UI/壳桥、决策与图像能力；解决具体聊天阻塞 | 能从发布清单追溯提交、两端构建和备份；一条普通聊天与一条能力失败路径正常；无重复付费执行 |
| B · 0.30 消息身份 | 持久 message ID、模型投影隔离、runtime 显式迁移、主动消息引用演进 | 同内容消息身份不同；重开/换代保留身份；删除后旧引用不能命中新消息；旧 v1 答题仍可用 |
| C · 0.31 持久 GenUI | surface 创建/替换/关闭、revision、跨轮与跨端重建；一个持久图表流程 | 生成→本地操作→更新→刷新恢复；旧 revision 拒绝；没有业务写按钮 |
| D · 0.32 按需业务动作 | 先接一项已有原子回执的动作，例如创建待办 | 显式确认与操作 ID 绑定；双击仅一次；unknown 查询核对，不自动重发 |

版本是执行标签，正式构建前核对实际线上版本及 APK versionCode。若其他工作已占用版本，顺延；不把 0.28/0.29 再分配给尚未实现的消息身份或 surface。

## 3. A：当前能力收口

### 3.1 发布与工作区

按实际能力整理可追溯发布。核对线上二进制、APK、构建参数与提交来源，补实际发布记录。来源缺失的发布标记为待核对。

Android 的 Gradle 默认值不是发布版本。统一用 `ORG_GRADLE_PROJECT_chatVersionCode` / `ORG_GRADLE_PROJECT_chatVersionName` 注入；正式发布清单记录服务版本、APK versionName/code、两端 SHA-256、源码提交、数据格式和回退点。

### 3.2 LLM 自主选择与宿主授权

普通聊天继续由主模型依据真实工具目录决定表达、搜索和呈现方式，不新增显式聊天模式或每轮分类请求。

`decide` 仅作为有明确标签集合的可选能力。工具执行器中的 decision gate 与模型主动调用 `decide` 必须分别声明成本与启用策略，避免同一判断无意重复调用。默认只给明确需要评估的操作启用 gate；服务不可用时 advisory 可以返回降级信息，required 必须根据宿主授权策略处理。

授权证据已改为宿主签发的一次性票据（`internal/probe/approval.go`）：绑定会话、角色、工具名和规范化参数摘要，由 `POST /api/approvals` 在真实用户点击后签发，执行器消费一次即失效。工具参数里的布尔值不再构成授权，模型也无法调用该接口——它必须先有一次被真实记录下来的拒绝，票据才有对象可附着。语义参考 DeepSeek Harness 的 approval seam（MIT）：只有 `allowed-once`，没有 allow-always，缺失应答者时失败关闭；本项目额外把票据绑定到参数摘要。长期记忆候选、角色变更审核仍走原流程。评估概率只影响建议或风险策略，不能替代业务 guard。

### 3.3 能力目录与暂时不可用

统一四种状态：未配置、被策略禁止、已配置但暂时不可用、当前可用。前两种不开放执行；已配置的图像桥断线等情况保留健康解释，执行时明确失败且不自动重复生成。健康检查不得触发模型加载或推理。

插件 Manifest 声明请求的能力，宿主配置授予能力。`toolCapabilities()` 已改为由 `pluginapi.Policy` 推导（停用插件不贡献能力），`newPluginHost` 只授予显式批准的命名空间；声明不再直接变成授权。角色级逐轮准入仍未做——角色还没有能力字段，等 M3 的消息身份一起改；执行端权限交集要等 M2。进程内 Go 插件是受信代码，Host 接口不是操作系统沙箱。

先以搜索插件证明注册、准入、结果和关闭生命周期，随后迁图像、决策、Clock/Media，再逐步迁 Provider、Memory、Activities、Companion 与 UI 能力。完整业务插件化是目标；每批随功能交付，不把全部迁移作为 GenUI 或聊天改进的前置。

### 3.4 聊天与界面

沿用已改造的客户端与统一设计 token。新增执行状态、授权与产物交互时，按普通聊天、工具执行、图片展示和通知回跳四条路径检查相关行为。样式和布局调整按具体使用反馈推进。

陪伴表达继续使用近期完整对话、获批事实、事件/活动及来源时间。记录实际重复追问、换题后拉回、计划误当事实等问题，再调整参考选择和预算；不增加永久情绪评分、假离线经历或强制追问。

## 4. B：稳定消息身份

当前 `Session.ContextMessagesFrom` 依据 summary.Covered 构造有效上下文；普通摘要并不因此重排历史。后台追加也不改变已有消息索引。真正的问题是删除后索引可复用、跨代引用缺少身份，以及同内容消息不能靠内容 hash 唯一区分。

拟定 `message_id = msg_ + 128-bit crypto/rand 十六进制`，宿主在首次提交前分配并持久化。不依赖时间排序；展示顺序使用日志顺序。模型请求白名单投影明确去掉身份、删除标志及 UI 元数据。失败提交不对外发布 ID；一次提交内保持同一分配结果。

旧数据通过停机显式迁移生成 ID，迁移产物先写入新 runtime 代，完整校验后更新 manifest/format-index。迁移中断可读取同一暂存产物续作，不能每次重跑重发不同 ID。新 reader 可读取旧格式供预检/迁移，但普通启动不自动重写。不得把 `id` 塞进 version 1 并宣传旧二进制兼容。

升级前落实格式清单：runtime/manifest、history、turns、run events、life/topics 分别标明读写版本；存在新字段的严格解码文件必须显式升版。具体数字在编码前统一冻结，不能把已有 runtime v2 当成尚未实施的迁移。

当前历史是消息正文权威；身份状态与删除记录共用所选 runtime 代。保留消息 ID 不随代变；被摘要覆盖的消息按 floor 禁用交互，ID 稳定不授予访问资格。最新轮删除移除消息，记录失效身份；新消息即使占同一索引也拿新 ID。整会话删除遵守现有删除登记，不从旧代补回。

life/topics 过渡期可双写索引和 ID，但旧记录只有位置，不能凭当前位置自动认领新消息。无法证明旧绑定的记录只保留历史内容/会话导航，不允许更新 surface。携带 ID 的引用校验失败后禁止降级到索引校验。

## 5. C：持久界面设计

保持 chat-ui v1 作为一次性组件；v2 复用七种组件校验。首个完整流程选一个持久图表，待业务事实到显示投影的契约稳定后再接共同活动时间线。

LLM 只提交受限的 create/update/close 建议及完整内容。宿主生成 surface ID/revision/source；更新必须携带期望 revision 和当前会话内可用的 surface 引用，交互与更新均重新校验来源。组件深度、数量、字节上限延用 RFC 的初始预算并单独校验；不接受任意 HTML/JS、远程组件或 JSON Patch。

选择的存储方案：在当前选中的 runtime 代内增加**明确版本化的 history 提交记录**，允许同一提交包含最终 assistant 消息和经验证的 surface 变更。追加、同步成功后才发布消息与 surface。events 保留运行诊断，不作为重放 UI 的第二份权威。此方案需要扩展 history codec、重写/导出/删除工具，不能直接向旧版 JSONL 添加未知 kind。

surface 投影可由 history 重建：`surface_id`、`revision`、`creator_message_id`、`last_writer_message_id`、`request_id`、`lifecycle`、`content`。沿用真实 request/batch 标识，不凭空创建另一个 turn ID 系统。新建和更新来自已提交的最终回答；流式预览不落盘、不启用提交按钮。0.26 host followup 首版仍不生成 surface。

并发更新以 expected_revision 比较，宿主提交 current+1；两个客户端竞争只允许一个成功。明确提交用既有 SubmitTurn 去重，在入队和执行前重新检查 revision、来源、角色和 floor。ID 稳定不能绕过遗忘与活动重置。

删除与恢复规则：

- 创建消息被删：surface 整体失效；不能靠后续 update 重新创建。
- 更新消息被删：首版保守冻结该 surface，保留无删除内容的失效提示，要求新的明确创建；避免回放旧版本让 revision 回退。
- 来源被摘要覆盖/遗忘/活动重置：旧操作失效，按数据可见性政策只读或隐藏，ID 不能恢复旧授权。
- 重启/刷新：从选定代重建，同 revision 与关闭状态一致；不重新请求模型或执行工具。

本地展开、缩放、草稿零模型调用；草稿默认本地，不承诺跨设备同步。提交答案是只读对话；保存任务等业务按钮留到 D。

## 6. D：业务动作

先选已具备同状态原子回执的一种业务，例如 todo_add。宿主按钮定义 action 白名单、schema、角色/会话/来源/expected_revision 和规范化参数摘要。用户确认绑定这些字段及一次性 operation ID；重试查询同一 operation，不能生成新 ID 规避去重。

业务成功以业务回执为准。显示投影失败可重建；结果 unknown 时显示待核对，不自动重发。未具备原子回执的活动修改、人设和记忆不能复用普通答题通道直接执行。

## 7. 验证与双端发布

只保留关键流程：A 的授权/能力失败与聊天回归；B 的迁移重开和删除防误绑定；C 的创建更新恢复、旧 revision 拒绝和来源失效；D 的重复点击及业务成功后显示失败。界面走一条桌面/窄屏连续流程，既有七组件测试复用，不扩展完整矩阵。真实模型和真机验证单列，未做就明确缺口。

每次部署先通过 `go build ./...`、`go vet ./...` 与受影响包测试。停服后完整备份 `/var/lib/chat-agent` 和 `/etc/chat-agent`；配置备份限 root 读取且不进入仓库。项目锁是文件存在型锁，停服后只读检查残留，禁止用 flock 打开原锁路径做探测。

服务端发布新 release、切 current，检查 active、NRestarts=0、health；APK 自增 code，构建发布 app.apk/manifest.json，验证签名/哈希并切 android/current，属主按部署约定设为 chat-agent。报告给出两端标识、校验和及实际回退命令。即使只改网页也明确 APK 是否重新发布，不能默认跳过。

回退命令必须依据当次实际备份结构填写：停服→恢复数据及配置→切回旧服务 release→启动验收。数据格式变化不能只换二进制；恢复备份会丢弃备份后的新增数据，需先保留故障现场。Android 不降低 versionCode；需回退客户端时用旧代码构建更高 code。
